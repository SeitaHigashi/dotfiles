# NixOS on ZFS — SSD×1 + HDD×2 (mirror) layout / managed by disko

Reference: <https://wiki.nixos.org/wiki/ZFS> / <https://github.com/nix-community/disko>

The disk layout is managed declaratively with [disko](https://github.com/nix-community/disko).
Partitioning, zpool creation, dataset creation, and `fileSystems` generation all happen
from a single file, [disko/default.nix](../disko/default.nix).

## 1. Overview

```
SSD (NVMe/SATA, 1 unit)
 ├─ part1  1 GiB    EF00  EFI System Partition  → /boot
 ├─ part2  32 GiB   8200  swap (randomEncryption)
 ├─ part3  8 GiB          slog    … reserved only (becomes dpool's log vdev when useSlog = true)
 └─ part4  rest     BF00  rpool   … system ZFS pool (single vdev)

HDD ×2 (same capacity)
 └─ dpool : mirror(hdd1, hdd2)   … data ZFS pool
```

| Mountpoint | Dataset | Location |
|---|---|---|
| `/` | `rpool/root` | SSD |
| `/var` `/var/log` `/var/lib` | `rpool/var*` | SSD |
| `/tmp` | `rpool/tmp` (`sync=disabled`) | SSD |
| `/home` | `dpool/home` | HDD mirror |
| `/srv` | `dpool/srv` | HDD mirror |
| `/srv/minecraft` | `rpool/srv/minecraft` | SSD (see below) |
| `/nix` | `dpool/nix` or `rpool/nix` | depends on `nixPool` |
| `/boot` | vfat partition | SSD |

- **`/srv/minecraft` alone lives on SSD.** The HDD (`ST4000DM004`) is SMR, and Minecraft's
  autosave was blocking in `write(2)` for over 60 seconds, causing the server to be killed
  by its own watchdog (see the
  [decision record](decisions/2026-07-31-minecraft-restarting-on-60s-tick.md)). Since rpool
  has no redundancy, syncoid in `modules/replication.nix` replicates it daily to
  `dpool/backup/minecraft`.

- **Read cache is ARC (RAM) only.** We do **not** use an SSD-backed secondary cache
  (L2ARC / cache vdev). We used to dedicate part5 as dpool's cache vdev, but in production
  this was the trigger for an unbootable-system incident, so it was removed (see the
  [decision record](decisions/2026-07-30-nvme-dropout-made-system-unbootable.md)). If read
  performance is insufficient, raise `arcMaxBytes` (i.e. RAM) instead of adding a cache
  vdev.
- **SLOG**: only helps synchronous writes (NFS servers, DBs). Nearly useless for desktop
  workloads, so it is **reserved only by default**.

### Do not do this (important)

**Do not add a `special` vdev (metadata-only vdev) to dpool backed by a single SSD.**
Unlike `cache`/`log`, `special` becomes part of the pool. If the SSD dies, **the whole
HDD mirror is lost with it**. If you want this, mirror two SSDs for it.
[disko/default.nix](../disko/default.nix) deliberately does not use one.

### About putting `/nix` on HDD

Toggled via `nixPool` in `machine.nix` (= `NIX_POOL` in `disks.env`).

Reads are absorbed by ARC (RAM-resident cache), so anything touched once effectively runs
at RAM speed. What stays at HDD speed:

- **Writes in general** — unpacking build outputs, `nix copy`, substituter fetches
- **`nix-collect-garbage`** — mass unlinks = metadata writes
- **First read right after boot** — ARC is volatile, so it is cold on every boot

Felt difference: `nixos-rebuild switch` is roughly 2-4x slower than SSD, GC is several to
tens of times slower, everyday operation is nearly the same.

Even so, **`nixPool = "dpool"` (HDD) is recommended**. The nix store takes heavy write
traffic from builds and GC, and keeping it on SSD noticeably shortens SSD lifespan —
especially with a budget SSD.

**Decide this at install time.** Moving it later requires `zfs send | zfs recv`.

## 3. Reading the disko layout

Things worth knowing about [disko/default.nix](../disko/default.nix).

### 3.1 Topology and "reserved partitions"

disko's `_create` verifies that **every partition declaring `pool = "..."`** appears in
the topology, and skips pool creation with `not all disks accounted for` if they don't
match.

That's why, when SLOG is unused, part3 is left as a **plain reserved region** with no
`content`:

```nix
slog = {
  priority = 3;
  size = m.slogSize;
  content = lib.mkIf m.useSlog { type = "zfs"; pool = "dpool"; };
};
```

Setting `useSlog = true` attaches `content` and simultaneously adds it to the topology's
`log`.

### 3.2 Full-path member specification

In the topology, `members` not starting with `/` resolve to
`/dev/disk/by-partlabel/disk-<disk-name>-zfs`. Since the SSD has multiple zfs partitions,
SLOG is specified with a **full path**:

```nix
log = [ { members = [ "/dev/disk/by-partlabel/disk-ssd-slog" ]; } ];
```

The HDD side is an exception and can use `members = [ "hdd1" "hdd2" ]` by name (each
disk's zfs partition is named `zfs`, so the rule above resolves it correctly).

### 3.3 mountpoint=legacy

Every dataset sets `options.mountpoint = "legacy"`, and actual mounting is unified through
the `fileSystems` disko generates. This avoids the mount-unit conflicts between
`zfs-mount.service` and systemd mount units that the `zfsutil` approach is prone to.

### 3.4 `/nix` properties

As the NixOS wiki instructs, the `/nix` dataset does not set the non-POSIX properties
(`normalization`, `utf8only`, `atime=off`, `snapdir=visible`, `acltype=nfsv4`). It uses
`relatime=on` instead of `atime=off`, and the store is excluded from snapshots since it is
reproducible from the flake.

## 4. Per-dataset rationale

Beyond the top-level layout in §1, several service-specific datasets in
[disko/default.nix](../disko/default.nix) split off from their parent for reasons worth
recording:

| Dataset | Pool | Why split off | Properties |
|---|---|---|---|
| `var/lib/victoriametrics` | rpool | Constant writes would bloat hourly snapshots of `var/lib` for data that's fine to lose; also drops out of syncoid's `rpool/var/lib` replication (non-recursive) | `recordsize=16K` (matches small time-series writes; default 128K rewrites 128K per small update) |
| `var/lib/loki` | rpool | Same two reasons as VictoriaMetrics | `recordsize=16K` |
| `var/lib/ollama` | rpool | GGUF files are multi-GiB and re-fetchable via `ollama pull`; also excluded from replication | `recordsize=1M` (large sequential reads), `compression=off` (quantized GGUF is already near-incompressible) |
| `comfyui` | dpool | Checkpoints run tens to 100+ GiB; rpool is single-vdev with finite capacity. I/O is bulk/low-frequency/non-realtime (unlike Minecraft's watchdog-sensitive small writes), so the SMR HDD is an acceptable trade — at the cost of somewhat slower checkpoint loads than NVMe | `recordsize=1M`, `compression=off` (safetensors is already near-incompressible) |
| `var/lib/openviking` | dpool | dpool's mirror provides redundancy; no snapshot layer wanted (same call as ComfyUI). Writes are async, post-session — not a realtime-watchdog workload like Minecraft. Revisit moving to rpool if writes stall in practice | `com.sun:auto-snapshot=false` |
| `backup` (both pools) | rpool & dpool | Receive-side parent for syncoid (see §6); `mountpoint=none` so a received dataset can never accidentally shadow-mount over the live `/` or `/var` | — |

Mount-path quirks worth knowing:

- **`var/lib/victoriametrics` and `var/lib/ollama` mount at `/var/lib/private/<name>`, not
  `/var/lib/<name>`.** Both services run with `DynamicUser=true`, under which systemd
  places the real directory at `/var/lib/private/<name>` and symlinks `/var/lib/<name>` to
  it. Mounting a real directory (i.e. a ZFS mountpoint) directly at `/var/lib/<name>` makes
  systemd's private-dir rename fail with `EBUSY` (`Device or resource busy`) since a mount
  point can't be renamed. So the mount targets the private path directly; the dataset name
  itself stays `rpool/var/lib/victoriametrics` (no `private` in the name — harmless since
  `mountpoint=legacy` decouples name from mount target).
- `var/lib/loki` and `comfyui` don't need this treatment: both run under fixed (non-Dynamic)
  users, confirmed in the respective NixOS modules.

`srv` and `backup` on both pools are parent-only, `mountpoint=none` placeholders — disko and
`zfs recv` don't auto-create intermediate datasets, so the parent must be declared
explicitly.

## 5. ARC and NVMe tuning ([modules/zfs.nix](../modules/zfs.nix))

- **`zfs_arc_max`** = `arcMaxBytes` from `machine.nix`, sized to roughly 1/4-1/2 of physical
  RAM per host.
- **`zfs_arc_sys_free`** = `arcMaxBytes / 4`. ARC isn't accounted to any cgroup (see
  `modules/resource-priority.nix`), so squeezing other services' `MemoryHigh` doesn't free
  it, and by default ARC barely leaves any free memory behind. Setting
  `zfs_arc_sys_free` forces ARC to keep that much memory free proactively. Added 2026-08-08
  after observing `/proc/pressure/memory` degrade while ComfyUI was running.
  `zfs_arc_shrink_shift` is left at its default (auto) since `zfs_arc_sys_free` alone is
  enough for "let go early," and a fixed shrink step risks hurting the cache hit rate.
- **`nvme_core.default_ps_max_latency_us=0`** — disables APST, working around a known issue
  where NVMe drives fail to resume from a low-power state and drop out. Kept permanently
  (negligible power cost) even after replacing the failing SSD; see the
  [NVMe dropout decision record](decisions/2026-07-30-nvme-dropout-made-system-unbootable.md).
- **`nvme_core.io_timeout`** is left at its 30s default. It was previously raised to 255s to
  stop a DRAM-less SSD's SLC-cache-exhaustion stalls from being misread as a failure; that
  drive has since been replaced, and DRAM-backed SSDs don't exhibit the stall, so keeping the
  default surfaces a real failure within seconds instead of hiding it for up to 4 minutes.
- **smartd** runs with `-a -o on -S on -n standby -W 4,50,60` (all attributes, offline
  self-test, autosave, don't wake idle HDDs, log/warn on a 4°C jump or crossing 50/60°C).
  No mail transport is configured, so warnings only reach the journal
  (`journalctl -u smartd`). This exists because the NVMe-dropout incident's drive had reached
  78% Percentage Used with nobody noticing.

## 6. Replication (syncoid) — [modules/replication.nix](../modules/replication.nix)

rpool is a single vdev with no redundancy (§1); if the SSD dies the whole system goes with
it (`/home` and `/srv` survive on dpool). syncoid replicates `services.zfs.autoSnapshot`'s
snapshots from rpool to `dpool/backup/*` daily, locally (no network involved),
`--no-sync-snap` so syncoid doesn't create its own snapshot generations on top of
autoSnapshot's. **This is not a backup** — it's same-chassis replication, so it does
nothing against fire, theft, or whole-enclosure failure; it only makes SSD-failure recovery
fast. Take real backups to external media or another host separately.

Replicated: `rpool/root`, `rpool/var/lib`, `rpool/srv/minecraft` (see the
[Minecraft decision record](decisions/2026-07-31-minecraft-restarting-on-60s-tick.md) for
why the Minecraft world lives on rpool at all — this replication is its only redundancy).
`rpool/srv/minecraft` can be replicated more often than daily by setting
`services.syncoid.commands."rpool/srv/minecraft".interval` individually — do not change
`services.syncoid.interval` globally, as that also pulls in `rpool/root` and
`rpool/var/lib`.

Not replicated: `rpool/var/log` (unneeded for recovery, high churn), `rpool/tmp`
(`sync=disabled`, expected to vanish on reboot), `rpool/nix` (fully reproducible from the
flake — replicating the store would waste HDD space for no recovery benefit; `nixos-install`
is faster and more reliable).
